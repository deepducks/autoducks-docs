autoducks is runtime-agnostic by design. The agent scripts, provider implementations, and core utilities live in `.autoducks/` and are independent of any specific CI/CD platform. The runtime layer — the workflow files that wire triggers to scripts — is a separate concern.

**Currently supported runtime:** GitHub Actions. Other runtimes are planned.

<Aside type="note">
The instructions below cover the **GitHub Actions runtime**. If you are setting up on a different CI/CD platform, the `.autoducks/` directory installs the same way — only the workflow wiring differs.
</Aside>

## Prerequisites (GitHub Actions runtime)

- A repository hosted on GitHub (personal or org)
- `gh` CLI authenticated (`gh auth login`)
- An Anthropic API key (from [console.anthropic.com](https://console.anthropic.com/)) — or a Claude subscription token, or a custom Anthropic-compatible endpoint. See [LLM credentials](#llm-credentials).
- The [Claude Code GitHub App](https://github.com/apps/claude) installed on your repo

The pipeline runs fully on the default `repo` + `workflow` token permissions — no extra scopes required. A token with `read:org` scope, exposed to the workflow as `AUTODUCKS_ORG_TOKEN`, is **optional** and only needed for two `@org/team`-based features:

- **CODEOWNERS authz** — expanding `@org/team` entries in `.github/CODEOWNERS` when `security.codeowners` is enabled. See [Team-expansion token limitation](/reference/security#team-expansion-token-limitation).
- **Team-based reviewer routing** — auto-assigning reviewers to task/feature PRs from a GitHub team.

Without `AUTODUCKS_ORG_TOKEN`, both of these degrade gracefully: team entries are skipped (or PRs are created without auto-assigned reviewers) and a warning is recorded — the pipeline itself does not fail.

## One-line install

Run this from the root of your repository:

```bash
curl -fsSL https://raw.githubusercontent.com/deepducks/autoducks/main/scripts/install.sh | bash
```

This downloads the `.autoducks/` directory tree and copies the GitHub Actions workflow files to `.github/workflows/`.

### Install options

```bash
# Specify a different repo (if not running inside the target repo)
curl -fsSL .../install.sh | bash -s -- --repo OWNER/REPO

# Download files only, skip the setup checks
curl -fsSL .../install.sh | bash -s -- --no-setup
```

## What gets installed

| Path | Description |
|------|-------------|
| `.autoducks/` | Agent scripts, prompts, provider implementations, core utilities |
| `.autoducks/runtimes/github-actions/` | GitHub Actions workflow definitions (one per agent) |
| `.github/workflows/autoducks-*.yml` | Copies of the runtime workflows, placed where GitHub Actions expects them |
| `.github/ISSUE_TEMPLATE/` | Issue templates for feature and task issues |
| `scripts/` | `setup.sh`, `install.sh`, `smoke-test.sh` |

The runtime workflows in `.github/workflows/` are copies of the canonical definitions in `.autoducks/runtimes/github-actions/`. The setup script verifies they stay in sync.

## Setup checks

After installing, run `scripts/setup.sh` to validate your repository:

```bash
./scripts/setup.sh
```

The script checks and auto-creates what it can, and reports what requires manual action:

<Steps>

1. **ITS authentication** — verifies `gh auth status` (GitHub CLI). Fatal if missing.

2. **Required labels** — creates `Feature`, `Bug`, `Task`, `Draft`, `smoke-test`, and the stage labels if they don't exist.

3. **LLM provider secret** — checks that the repository has an LLM credential: `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, or a custom endpoint (`ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`). Each of these may live as a **repository secret or an organization secret** — see [Repository vs. organization secrets](#repository-vs-organization-secrets). This check reports one of three outcomes:
   - **Configured** — a credential resolved, either as a repository secret or an organization secret.
   - **"Could not verify the LLM credential"** — listing organization secrets was refused (needs org-owner access), so the script cannot tell whether an org-level credential covers this repo. This is *not* a failure: if the credential is in fact set at the organization level, the repository is fine.
   - **"No LLM credential is configured"** — no credential was found at either tier. Prints the command to add one:
     ```bash
     gh secret set ANTHROPIC_API_KEY --repo OWNER/REPO
     ```
   See [LLM credentials](#llm-credentials) for the three credential options.

4. **Runtime workflow permissions** — checks for `write` permissions and `can_approve_pull_request_reviews: true` on GitHub Actions. Prints the fix command if wrong.

5. **Claude Code GitHub App** — reminds you to install the app at [github.com/apps/claude](https://github.com/apps/claude). Cannot be verified programmatically.

6. **Issue types (Feature, Task)** — checks org-level issue types. Workflows run without them, but typed issue relationships won't appear in the issue tracker UI. Routing is driven by labels (which the Architect and Engineer apply automatically); the native type is a visual enhancement for org repos.

7. **Sub-issues API** — GitHub's native sub-issue relationship. Available
   on every GitHub-hosted repository as of October 2024. The Engineer
   uses this to link each task to its parent Feature so a progress bar and
   "Parent issue" backlink render in the GitHub UI. Autoducks probes at
   runtime and falls back to the markdown `## Progress` checklist if the
   API is unavailable, so no manual setup is required.

8. **Runtime workflow sync** — verifies that `.github/workflows/autoducks-*.yml` match `.autoducks/runtimes/github-actions/`. Fails if out of sync.

</Steps>

<Aside type="tip">
After a successful setup, validate the full pipeline with the smoke test:

```bash
./scripts/smoke-test.sh --cleanup
```

This creates a test feature issue, runs it through the full design → plan → execution loop, and cleans up afterward.
</Aside>

## LLM credentials

Every LLM-backed agent reads its credential from repository secrets. Pick one of three setups:

| Setup | Secrets | When to use |
|-------|---------|-------------|
| Anthropic API key | `ANTHROPIC_API_KEY` | Default. Pay-as-you-go billing on the Anthropic API. |
| Claude subscription | `CLAUDE_CODE_OAUTH_TOKEN` | Reuse a Claude Code subscription. Generate it with `claude setup-token`. |
| Custom endpoint | `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` | Any Anthropic-compatible gateway, proxy, or self-hosted relay. |

```bash
# Custom endpoint
gh secret set ANTHROPIC_BASE_URL   --repo OWNER/REPO   # e.g. https://gateway.internal/anthropic
gh secret set ANTHROPIC_AUTH_TOKEN --repo OWNER/REPO   # sent as: Authorization: Bearer <token>
```

The base URL is not sensitive, so it can also be a repository **variable** (`gh variable set ANTHROPIC_BASE_URL`) — the workflows read the secret first and fall back to the variable. Gateways that authenticate with the `x-api-key` header instead of a bearer token take `ANTHROPIC_API_KEY` alongside `ANTHROPIC_BASE_URL`, with no `ANTHROPIC_AUTH_TOKEN`.

<Aside type="caution">
`ANTHROPIC_BASE_URL` wins over `CLAUDE_CODE_OAUTH_TOKEN`. A subscription token is only valid against `api.anthropic.com`, and Claude Code prefers it over the API key — so when a custom endpoint is configured, the agents drop the OAuth token and send the custom credential instead. Set the model in `.autoducks/autoducks.json` (or per run with `model:`) to whatever your gateway exposes.
</Aside>

### Repository vs. organization secrets

Every credential above (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`) can be set as a **repository secret** or an **organization secret**. GitHub resolves a name at run time in this order: **environment > repository > organization** — the first tier that defines the name wins, regardless of which tier was set most recently.

An organization secret only reaches a given repository if its visibility is `all`, or is `selected` and that repository is on the list.

<Aside type="caution">
**Free-plan caveat:** on a Free organization, an organization secret reaches **public** repositories only — even when its visibility is `selected` and a private repository is on the list. GitHub's API accepts adding a private repository to a secret's `selected` list without any error, but the value resolves **empty** at run time in that repository, which fails silently (the agent step errors with no credential, not with a clear "wrong tier" message).

Fix one of two ways:
- Add the same credential as a **repository-level secret** instead — repository secrets behave identically on public and private repos regardless of plan:
  ```bash
  gh secret set ANTHROPIC_API_KEY --repo OWNER/REPO
  ```
- Upgrade the organization to **Team or Enterprise**, where organization secrets reach private repositories normally.
</Aside>

**Shadowing:** if a repository-level secret and an organization-level secret share the same name, the repository copy always wins (per the precedence order above) and the organization copy is silently ignored for that repo. A common failure mode is a leftover repository-level secret from before the credential was centralized at the org level — rotating the organization secret then has no effect on that repository until the repository-level copy is removed.

## Updating

Re-run the install script to update to the latest version:

```bash
curl -fsSL https://raw.githubusercontent.com/deepducks/autoducks/main/scripts/install.sh | bash
```

It detects the existing `.autoducks/autoducks.json` and runs in update mode (skips setup).

<Aside type="tip">
Updates overwrite `.autoducks/` and `.github/workflows/autoducks-*.yml` wholesale, but preserve `.autoducks/autoducks.json`, `.autoducks/providers/llm/claude/settings.json`, `.autoducks/custom/`, and anything under `.github/actions/`. See the [Customization guide](/guides/customization#the-update-survival-guarantee) for what those consumer-owned files are and why they survive.
</Aside>

## Configuration

After installing, you can customize defaults in `.autoducks/autoducks.json`:

```json
{
  "command": "",
  "providers": {
    "its": "github",
    "git": "github",
    "llm": "claude"
  },
  "defaults": {
    "model": "claude-sonnet-5",
    "effort": "high",
    "base_branch": "main"
  }
}
```

See [Configuration reference](/reference/configuration) for all options.

<Aside type="tip">
**Fork workflow:** working from a fork and want PRs to land on a fork-local branch instead of going straight upstream? Set `defaults.integration_branch` — see [`defaults.integration_branch`](/reference/configuration#defaultsintegration_branch) in the Configuration reference.
</Aside>
